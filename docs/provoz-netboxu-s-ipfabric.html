Kapitola 1

Jak to funguje

IP Fabric objevuje síť a drží její skutečný stav. NetBox drží stav zamýšlený — inventář, vlastníky, komunikační matici a historii kontrol. Data putují jedním směrem, z IP Fabricu do NetBoxu.

IP Fabric APItabulky snímku se stahují dotazem na /api/tables/…, každý dotaz je vázaný na konkrétní snímek
push_ipf_data.pynáš skript, mapuje jedenáct tabulek IP Fabricu na endpointy pluginu a ukládá řádky tak, jak jsou
IPFabricDatasurová data uvnitř NetBoxu, ještě to nejsou zařízení ani adresy — jen řádky čekající na zpracování
transform mapypředpis pluginu, jak z řádku vznikne objekt NetBoxu: která pole, jaké vazby, podle čeho se páruje s existujícím
větevingesce nezapisuje do ostrých dat, nejdřív postaví návrh změn stranou
merge do Mainteprve sloučení větve promítne změny do NetBoxu, se kterým pracují lidé
Režim zdroje je „remote", ne „local".

Plugin umí data tahat sám (režim local), ale k tomu potřebuje na straně IP Fabricu oprávnění číst /api/tables/management/snapshots. Na demo serveru ho nemáme — vrací 403 API_INSUFFICIENT_RIGHTS. Proto je zdroj nastavený jako remote a data do něj vkládá náš skript. Na firemní instanci má smysl o to oprávnění požádat a přejít na local; zbytek řetězce zůstane stejný.

Kapitola 2

Proč nelze importovat soubor snímku přímo

IP Fabric umí snímek stáhnout jako soubor — v UI u snímku volbou Download, přes API dotazem na /api/snapshots/<id>/download. Nabízí se otázka, proč ten soubor prostě nerozbalit a nenapsat si vlastní import v Pythonu. Odpověď má čtyři vrstvy a každá sama o sobě stačí k tomu, aby se do toho člověk nepouštěl.

Ten soubor není formát pro výměnu dat

Je to interní archiv určený k nahrání zpátky do IP Fabricu, typicky na jinou instanci téhož produktu. Není to dokumentovaný formát, výrobce ho nepopisuje jako rozhraní a negarantuje jeho stabilitu. Co se v něm přečte dnes, nemusí platit po upgradu na další verzi.

Rozbalení by znamenalo zpětné inženýrství bez záruky

Napsat parser nedokumentovaného formátu jde. Udržovat ho přes verze produktu, na kterém stojí důkazní řetězec pro NIS2, je něco jiného. První upgrade IP Fabricu, který změní vnitřní strukturu, shodí import a nikdo předem neřekne, kdy to nastane. U nástroje, jehož výstupem má být doklad pro auditora, je to nepřijatelné riziko.

Stejná data jsou dostupná dokumentovaným rozhraním

To podstatné: všechno, co v archivu je, se dá přečíst přes API — a API je verzované, popsané a vázané na konkrétní snímek. Každý dotaz na tabulku přijímá parametr snapshot, takže i starý snímek je dotazovatelný, dokud je v IP Fabricu nahraný. Psát parser archivu znamená podstoupit velké riziko pro data, která jsou k dispozici bezpečnou cestou.

A hlavně: čtení souboru není ta těžká část

Kdyby se archiv rozbalil, pořád bys měl jen tabulky. Práce, která z nich dělá použitelný inventář, je jinde — jak z řádku udělat zařízení, jak k němu přiřadit lokalitu, typ, platformu a rozhraní, podle čeho poznat, že tohle zařízení už v NetBoxu je, a co se má aktualizovat místo založení nového. Přesně to dělají transform mapy pluginu a je to několik set řádků logiky, kterou by vlastní import musel napsat znovu — včetně větvení, párování a zpracování chyb.

Závěr: formát souboru není překážka, kterou má smysl překonávat.

Potřebu „mít snímek na disku a umět ho nahrát i bez připojení" jsme vyřešili jinak a bezpečně — stažením tabulek přes API do JSON souborů. Popsáno v kapitole 4.

Kapitola 5

Komunikační matice

Matice je seznam tvrzení o tom, co spolu smí a nesmí komunikovat. Kontrola pak každé tvrzení ověří simulací cesty v IP Fabricu a porovná se skutečností. Formát je záměrně triviální, aby se dal udržovat i mimo IT:

name,src,dst,proto,port,expected
Sprava - SSH na pristupovy switch L35,10.39.255.1,10.35.255.194,tcp,22,allow
Sprava - telnet na L35 je zakazan,10.39.255.1,10.35.255.194,tcp,23,deny

Odkud se bere za normálních okolností

Matici nevyrábí síťař. Je to dokument zákazníka a vzniká ze tří zdrojů, obvykle kombinací:

  • Architektura aplikací. Vlastník systému ví, že aplikační server potřebuje na databázi a kam se hlásí uživatelé. Tohle je jediný zdroj, který říká, co má platit — zbylé dva říkají, co platí.
  • Workshop s aplikačními týmy. Tam, kde dokumentace není, se matice sepisuje při jednání. Bývá to nejpracnější část celého zavedení a obvykle se poprvé dělá až kvůli NIS2.
  • Export pravidel ze stávajícího firewallu. Popsáno v kapitole 6. Pozor na záměnu: z firewallu se nedozvíš, co má platit, jen co kdysi někdo povolil.

Odkud ji bereme my pro demo

Zákazníka nemáme, takže matici skládáme z topologie, kterou jsme právě naimportovali. Postup je jednoduchý: z NetBoxu se vytáhne přehled lokalit, rolí zařízení a podsítí, a podle něj se napíší řádky, které dávají v takové síti smysl — správa prvků, provoz mezi pobočkami, infrastrukturní služby, přístup do cloudu a segmentační zákazy.

Přehled topologie jako podklad pro matici 
cd /opt/netbox-docker && docker compose exec -T netbox \
  /opt/netbox/netbox/manage.py shell <<'PY'
import collections
from dcim.models import Site, Device
from ipam.models import IPAddress
for s in Site.objects.order_by('name'):
    print(f'{s.name:<34} {s.devices.count()}')
for r, n in collections.Counter(str(d.role) for d in Device.objects.all()).most_common():
    print(f'{r:<20} {n}')
c = collections.Counter()
for a in IPAddress.objects.all():
    if a.address.version == 4:
        c[str(a.address.ip).rsplit('.', 1)[0] + '.0/24'] += 1
for k, v in sorted(c.items()):
    if v >= 3:
        print(f'{k:<18} {v}')
PY
Matice je vázaná na snímek.

Adresy v matici musí existovat v tom snímku, proti kterému se kontroluje. Matice psaná pro první snímek (matice-demo.csv, adresy 10.194.56.x a 172.16.4x.x) v druhém snímku nedává smysl — proto je pro něj samostatný soubor matice-demo2.csv.

Kapitola 6

Matice z pravidel firewallu

Druhý směr: místo ověřování hotové matice se vezmou existující pravidla a pro každé se hledá opora. Tomu se říká obrácená kontrola a v auditu bývá nejvýnosnější, protože odhalí pravidla, která tam kdysi někdo dal a nikdo neví proč.

Postup

  1. Export pravidel. IP Fabric má tabulky bezpečnostních pravidel za každé zařízení, takže export nemusí jít přes správce firewallu — dá se vytáhnout ze snímku stejnou cestou jako inventář.
  2. Převod na kandidátní řádky. Z každého pravidla vznikne řádek ve tvaru matice: zdroj, cíl, protokol, port, a expected=allow, protože pravidlo tvrdí, že to má procházet.
  3. Porovnání se schválenou maticí. Řádky, které v matici oporu mají, jsou v pořádku. Řádky bez opory jsou nález — buď matici doplnit, nebo pravidlo zrušit.
  4. Ověření průchodnosti. U pravidel, která zůstanou, se ještě ověří, jestli vůbec něco dělají. Pravidlo, přes které nevede cesta, je mrtvé a jen zvětšuje plochu k auditu.
Rozdíl, na kterém záleží.

Matice odvozená z firewallu není schválená matice. Je to soupis současného stavu, který teprve někdo musí potvrdit nebo odmítnout. Kdo obojí zamění, získá dokument, který sám sebe potvrzuje a auditorovi neřekne nic.

Tato část zatím není zautomatizovaná — je to nejbližší krok, který má smysl dodělat. Vyžaduje doplnit mapování tabulek bezpečnostních pravidel do push_ipf_data.py a napsat převodník na formát matice.

Kapitola 8

Známá omezení a potíže

ProjevPříčina a řešení
Ingesce skončí stavem timeout, nic se nesloučí Výchozí RQ_DEFAULT_TIMEOUT 300 s nestačí na velký snímek. Nastaveno na 7200 v /opt/netbox-docker/configuration/extra.py, mění se restartem kontejnerů.
Sync uvázne ve stavu ready_to_merge a tlačítko Synchronize je mrtvé Někdo sloučil větev přímo přes branch.merge() a obešel tím stavový automat pluginu. Správná cesta je enqueue_merge_job(), což dělá auto_merge sám. Náprava: přepsat stav syncu na completed.
Zdroj hlásí Selhalo Kosmetika režimu remote — plugin zkusí stáhnout seznam snímků, dostane 403 a poznamená si neúspěch. Na data to nemá vliv. Na stránce zdroje nemačkej Synchronizovat, to je synchronizace snímků, ne import dat.
Přibývají duplicitní VRF při každém běhu VRF se páruje na dvojici jméno + RD. Prázdné RD musí do NetBoxu přijít jako None, ne jako prázdný řetězec — jinak se shoda nikdy nenajde. Proto rd nesmí být v množině TEXTOVE_SLOUPCE v našem skriptu.
Zařízení padá na null value in column "serial" Filtr pluginu zahodí sériové číslo delší než 50 znaků a sáhne po sloupci id, který mu ale ořezání dat nepředá. Opraveno v transform mapě: platné sériové číslo, jinak zkrácený hostname.
Zařízení padá na délce jména (151 znaků) Plugin rozlišuje zařízení se stejným jménem tak, že za jméno přilepí - (sériové číslo). U azurových prostředků, jejichž identifikátor je celá cesta k prostředku, výsledek přeteče limit 64 znaků. Týká se jednoho objektu z 365, zatím neřešeno.
VLAN padá na vid must be >= 1 V datech jsou tři VLAN s ID nula. Nejsou to VLAN, je to artefakt — filtrují se už při plnění dat.
Tlačítko Browse nereaguje při nahrávání souboru Firefox v Ubuntu je snap a výběr souboru jde přes xdg-desktop-portal, který ve vzdáleném sezení často neběží. Obejito polem cesta ve skriptu — soubor se čte přímo z kontejneru.
Nepřiřazené IPv6 adresy (link-local) IP tabulka udává zkrácené jméno rozhraní (Gi0/1), NetBox má GigabitEthernet0/1. Pro komunikační matici jsou link-local adresy nepodstatné, neřešíme.
Endpoint managed-networks hlásí nedostupnost Neznáme správný název té tabulky v API 7.9. Důsledek: prefixy se neimportují. Ostatní endpointy tím nejsou dotčené.
Doplňující dokumentace ke stacku samotnému — spouštění, zálohy, hesla, změny verzí — je v souboru /opt/netbox-docker/README.txt. Skripty a datové soubory jsou v /opt/commatrix/.
